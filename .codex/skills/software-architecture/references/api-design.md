# API 与跨边界契约设计

## 设计原则

- 从消费者任务和业务语义开始，不从数据库表或当前函数签名直接生成公开契约。
- 将协议、数据模型、错误模型、安全、兼容性和运行行为视为同一个契约。
- 优先遵循项目已有风格和版本策略；不要在同一系统中无理由引入新的接口范式。
- 示例数据使用虚构值，不写入真实密钥、个人信息、内部地址或本机路径。

## 设计流程

1. 确认消费者、调用场景、同步或异步需求、数据敏感度和可用性要求。
2. 选择适合现有系统的契约形式：HTTP、RPC、GraphQL、事件、消息、Webhook、CLI 或设备协议。
3. 定义资源、操作、消息或命令的语义，不泄漏不稳定的内部实现。
4. 定义请求、响应、事件载荷、字段约束、默认值、空值、精度、时间、排序和编码。
5. 定义认证、授权、租户或主体边界，以及敏感数据的最小暴露。
6. 定义错误分类、状态或错误码、可重试性、幂等性、超时、取消和重复投递行为。
7. 定义分页、过滤、排序、限流、批量、并发和资源上限中适用的部分。
8. 定义版本、兼容性、弃用、迁移和消费者升级策略。
9. 定义日志、指标、追踪和审计要求，避免在可观察性数据中泄露敏感内容。
10. 产出机器可读契约、示例和契约测试要求，并等待确认。
