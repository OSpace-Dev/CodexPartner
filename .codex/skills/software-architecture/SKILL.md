# 软件架构与设计

在需求确认后、交付规划前确定系统如何组织以及为什么这样设计。架构阶段产出方案和决策，不直接修改产品代码。

## 设计准入

开始设计前确认：

- 需求目标、范围、非目标和关键验收条件已经确认。
- 产品行为、安全、数据、成本等阻塞性问题已经决定，或明确列为待决策项。
- 已读取适用的 `AGENTS.md`、现有架构、接口、数据、部署和历史决策文档。

需求仍不清晰时使用 `$software-delivery` 继续澄清，不用技术方案替代产品决策。

## 设计深度

选择最小但足够降低风险的设计层次：

- 无独立设计：局部、低风险、不改变边界或契约的变更；在任务中记录影响和实现约束即可。
- 简要设计：单个组件内存在多种实现方式，需要记录关键选择和验证方式。
- 架构或概要设计：跨模块、跨服务、公开接口、数据模型、部署拓扑或重要质量属性发生变化。
- 详细设计：复杂状态机、并发、算法、迁移、协议、性能关键路径、硬件接口或不可逆操作。

不要为简单改动制造形式化文档，也不要以“改动不大”为由跳过高风险设计。

## 设计流程

1. 建立现状模型。记录现有系统边界、组件职责、接口、数据流、部署关系和已知约束；用代码、配置、测试和有效文档作为证据。
2. 提取设计驱动因素：功能需求、质量属性、规模、性能、安全、可靠性、兼容性、运维、成本、硬件或平台限制。
3. 选择设计深度，并说明为什么需要或不需要独立架构、概要设计和详细设计。
4. 对有实质差异的方案进行比较。说明收益、代价、风险、迁移和回退；不要为了凑数量制造虚假备选方案。
5. 描述目标设计：系统上下文、组件与职责、接口契约、数据模型与流向、错误和故障处理、部署拓扑、可观察性及安全边界。
6. 对需要详细设计的部分补充模块内部结构、状态转换、时序、并发、资源生命周期、算法、迁移步骤和边界条件。
7. 将关键选择记录为决策，明确背景、备选方案、结论、后果和复查条件。高影响选择必须等待用户或负责人确认。
8. 检查需求可追溯性和可验证性。每个关键设计点应关联需求、风险、验收或验证方法。
9. 设计确认后，使用 `$delivery-planning` 将方案拆分为里程碑和任务。

## API 与跨边界契约

变更涉及 HTTP API、RPC、GraphQL、事件、消息、Webhook、CLI 契约或设备协议时，读取 [references/api-design.md](references/api-design.md)。先确认消费者、用例和兼容性，再定义协议细节；API 设计得到确认前不进入实现。

API 设计文档正文编号使用 `API-YYYYMMDD-NNN`。OpenAPI、AsyncAPI、Protocol Buffers、GraphQL Schema 或其他机器可读契约应作为架构交付物，并使用仓库相对路径与设计文档互相链接。

## 设计边界

- 不臆造流量、数据规模、用户角色、SLA、硬件能力或外部系统行为；未知内容应请求确认或明确标注。
- 优先延续现有架构和约定；引入新组件、依赖、协议或基础设施时必须说明必要性和长期成本。
- 区分当前架构、目标架构和过渡架构，避免把未来设想写成已经存在的事实。
- 设计接口时明确输入、输出、错误、版本、兼容性、超时、重试、幂等性和安全边界中适用的部分。
- 设计数据变化时明确模式演进、迁移、校验、备份、回退或兼容前滚策略。
- 架构文档中的仓库文件链接和路径必须使用仓库相对路径，不得写入盘符、用户目录或其他本机绝对路径。

## 设计交付

根据所选深度产出以下一个或多个文档：

- 架构设计：`ARCH-YYYYMMDD-NNN`
- 概要设计：`HLD-YYYYMMDD-NNN`
- 详细设计：`LLD-YYYYMMDD-NNN`
- 关键决策：`DEC-YYYYMMDD-NNN`
- API 契约：`API-YYYYMMDD-NNN`

文件使用 `YYYY-MM-DD-NNN-topic.md` 命名。使用 [references/architecture-guide.md](references/architecture-guide.md) 选择设计内容和模板。
