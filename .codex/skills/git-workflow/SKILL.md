# Git 工作流

以 Git 自身为通用基础，按仓库实际远端选择 GitHub、GitLab、Gitee 或自建服务能力。保护用户现有改动和远端历史，不把托管平台特性写成 Git 的必要条件。

## 工作流程

1. 读取 `AGENTS.md` 中的分支、提交、远端、评审和发布规则。
2. 检查仓库状态、当前分支、工作树、暂存区、最近提交和远端配置。区分当前任务改动与用户已有改动。
3. 识别托管平台和可用工具。优先使用标准 Git；只有相关 CLI、API、认证和项目约定都存在时才使用平台专用能力。
4. 在执行会改变状态的操作前说明目标和影响。提交、推送、合并、打标签、删除分支、修改远端和重写历史必须符合用户授权与仓库规则。
5. 操作后重新检查状态、分支、提交和远端结果，报告实际完成内容和未完成事项。

## 仓库与远端

- 初始化新仓库前确认目标目录，并先建立适用的 `.gitignore`、默认分支和隐私规则。
- 使用仓库证据识别远端，不根据域名猜测权限、产品版本或 API 能力。
- 支持多个远端时明确每个远端用途，例如主要仓库、镜像或只读上游；推送前显示目标远端和分支。
- 远端地址不得包含明文凭据。SSH 主机、令牌和账号配置保存在用户环境或凭据管理工具中，不写入项目文档。
- GitHub 可使用 `gh`，GitLab 可使用 `glab` 或兼容 API；Gitee 和自建服务按实际可用工具处理。平台工具不可用时退回标准 Git 和人工网页流程。

## 提交

1. 提交前检查完整差异、未跟踪文件和相关验证结果。
2. 扫描密钥、凭据、本机绝对路径、用户目录、调试输出和不应提交的生成文件。
3. 只暂存当前任务文件。不得为方便而覆盖、丢弃或混入来源不明的用户改动。
4. 检查暂存差异，确认提交内容与任务目标一致。
5. 按项目语言和格式编写说明结果的提交信息，避免无意义描述。
6. 形成小而完整、可回退的提交；不要为了追求单一提交而隐藏多个独立问题。

## 同步、合并与发布

- 获取远端信息和读取历史可以作为诊断；会改变工作树或历史的 pull、rebase、merge 等操作先检查冲突风险。
- 推送前确认远端、分支、提交范围和是否包含上游变化。未经授权不推送远端。
- 合并前确认评审和测试门槛。冲突解决属于代码变更，必须重新检查差异并执行受影响验证。
- 标签必须指向明确、已验证的提交，并遵循仓库版本规则；未经确认不创建或推送发布标签。
- Pull Request 或 Merge Request 描述关联需求、任务、评审、测试和风险；不在多个平台复制维护不同事实。

## 安全边界

- 不使用 `reset --hard`、`clean`、强制推送、历史重写或批量删除来处理不理解的状态。
- 确需重写历史时，先说明提交范围、协作者影响、备份或恢复方式，并取得明确确认。
- 不修改全局 Git 配置，除非用户明确要求；项目规则优先使用仓库级配置。
- 不绕过受保护分支、签名、Review 或 CI 门槛。
- 文档和示例只使用仓库相对路径及通用远端占位符，不记录本机或内网身份信息。

使用 [references/git-guide.md](references/git-guide.md) 选择托管平台流程和执行检查项。重要的仓库迁移、远端变更或历史操作可以记录为 `GIT-YYYYMMDD-NNN`。
