# 代码质量

提高代码的正确性、可读性、可修改性和可验证性。尊重项目现有语言、框架和工具链，不把个人审美、机械指标或流行模式当成通用真理。

## 使用方式

1. 读取适用的 `AGENTS.md`、项目编码规范、格式化与静态检查配置，并检查同一模块中多个有效示例。
2. 明确当前任务行为和变更边界。质量改进服务于当前任务，不静默扩大为全仓库重构。
3. 按实际语言和技术域选择检查项；有语言或框架专项 Skill 时同时遵循。
4. 编码阶段可以在任务范围内改善问题；Review 阶段只报告发现，不直接修改代码。
5. 对需要跨模块或大规模处理的问题建立独立任务，说明收益、风险和验证方式。

## 核心原则

- 名称表达领域含义和职责，不泄漏偶然实现，也不用模糊缩写隐藏概念。
- 函数、类型和模块保持内聚，拥有一个清楚的变化原因；副作用和依赖应可见。
- 控制流保持直接，优先消除不必要嵌套、重复分支和难以组合的布尔开关。
- 数据和状态具有清楚的所有权、合法状态和边界；不要依赖隐含执行顺序。
- 错误应在合适边界被分类、传播或恢复，不吞掉异常，也不泄露敏感内部信息。
- 抽象必须减少真实重复或耦合。不要为假想未来建立空洞层次、万能接口或过度配置。
- 重复并非总比错误抽象更差；只有概念和变化原因一致时才合并。
- 注释说明原因、约束和反直觉行为，不重复代码字面含义，不保留失效叙述。
- 代码应便于测试和诊断，时间、随机、网络、存储和外部状态等依赖应在适当边界可控制。

## 常见坏味道

- 单个函数或类型承担多个不相关职责。
- 参数过多、布尔参数改变语义，或调用方必须知道隐藏顺序。
- 深层嵌套、重复条件、散落的魔法值和不完整的状态组合。
- 跨模块读取内部状态、循环依赖、全局可变状态和远距离副作用。
- 复制粘贴后细微分叉，或为消除两行重复建立复杂抽象。
- 捕获所有错误后忽略、返回含糊状态，或日志与返回值互相矛盾。
- 测试只能通过大量内部细节模拟，表明边界或职责可能不清楚。
- 留下死代码、注释掉的实现、无主兼容层或无法证明用途的配置开关。
- 为通过检查而降低类型、安全、测试或可观察性约束。

坏味道是调查信号，不是自动重构命令。必须结合行为、变化频率、风险和项目约定判断。

## 项目编码规范

用户要求建立规范时，将可机械执行的规则优先交给格式化、Lint、类型和静态分析配置；文档只保留工具无法表达的设计与协作原则。

规范文档使用 `YYYY-MM-DD-NNN-topic.md`，正文编号为 `STD-YYYYMMDD-NNN`。只写项目已经采用或用户确认的规则，不从单个文件推断全仓库约定。

使用 [references/code-quality-guide.md](references/code-quality-guide.md) 进行实现检查、Review 和规范编写。所有文档和代码位置使用仓库相对路径。
