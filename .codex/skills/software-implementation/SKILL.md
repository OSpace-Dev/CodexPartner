# 软件实现

以已确认任务为边界完成可验证的软件变更。本 Skill 只定义跨技术栈通用的实施纪律；具体框架、平台、硬件或协议规则由仓库指令和专项 Skill 补充。

## 实施准入

开始编码前确认：

- 目标、范围、非目标和完成定义明确。
- 影响产品行为、公开契约、数据、安全、成本或架构的决策已经确认。
- 必要依赖和前置任务已满足，或已有明确的隔离方案。
- 能说明至少一种验证改动的方法。

不满足准入条件时停止编码。需求不清晰时使用 `$software-delivery`；任务边界或顺序不清晰时使用 `$delivery-planning`。

## 实施流程

1. 读取适用范围内的 `AGENTS.md`、当前任务、需求、决策和技术文档。将其转化为本次变更的约束和验证清单。
2. 检查相关代码、测试、配置、接口和历史模式。不要仅凭任务标题推测实现位置或架构。
3. 识别技术域。加载仓库已有的专项 Skill 或规范；多个技术域交叉时分别应用，并明确接口边界。
4. 在较大改动前说明实施意图、预计修改范围和验证方式。发现计划与代码事实冲突时，记录证据并暂停相关部分，不要静默改写需求。
5. 建立基线。缺陷修复优先复现问题或增加失败测试；行为变更确认现有测试和构建状态；高风险操作确认回退路径。
6. 完成最小、内聚的代码改动。遵循既有命名、架构、错误处理和依赖模式，并使用 `$code-quality` 检查真实坏味道；不混入无关重构或格式化。
7. 边改边验证。先运行最接近改动的检查，再按风险扩大到类型检查、Lint、集成测试、构建、人工或目标环境验证。
8. 自我复核完整变更。检查正确性、错误路径、兼容性、安全、资源释放、并发、性能、可观察性和意外文件变更；只检查与当前技术域相关的项目。
9. 同步受影响的测试、配置、接口说明、需求、决策和任务状态。不要在多处复制同一事实。
10. 收口时说明改了什么、如何验证、未执行的验证、已知风险和后续事项。

## 技术域路由

按实际变更边界选择专项能力，不按仓库名称猜测：

- 前端：组件与状态、设计系统、交互、可访问性、响应式布局和浏览器验证。
- 后端：API 契约、鉴权、数据一致性、事务、幂等性、错误模型和可观察性。
- 系统与底层：内存、并发、资源生命周期、ABI、性能和平台兼容性。
- 嵌入式：硬件规格、工具链、时序、中断、功耗、存储限制、刷写和设备级验证。
- 数据与迁移：模式兼容、数据质量、可重入、回滚、批次控制和生产验证。

没有专项 Skill 时，优先遵循仓库代码、测试、官方工具链和项目文档，不在通用 Skill 中臆造领域规则。阅读 [references/domain-routing.md](references/domain-routing.md) 判断是否需要建立专项 Skill。

## 变更边界

- 不要擅自扩大任务范围或顺手修复无关问题；将新问题记录到 Backlog。
- 不要未经确认引入新依赖、改变公开接口、修改持久化格式或降低安全控制。
- 不要用大规模重写替代可以局部完成的变更；确需重构时单独说明收益、风险和迁移方式。
- 不要删除或覆盖来源不明的现有改动。
- 不要将密钥、凭据、机器专用路径或临时产物写入可提交内容。
- 不要为了让检查通过而削弱、跳过或伪造测试。

## 完成定义

只有满足任务的完成定义并形成证据时才标记完成。至少检查：

- 实现符合目标、范围和非目标。
- 相关测试通过；按风险完成类型检查、Lint、构建、人工或目标环境验证。
- 错误路径和关键边界已覆盖。
- 相关文档、任务状态和必要决策已同步。
- 未执行验证和剩余风险已明确说明。

执行前后使用 [references/implementation-checklist.md](references/implementation-checklist.md) 进行检查。

## 评审交接

完成开发者级验证和自我复核后，使用 `$software-review` 进行只读评审。评审发现不得在 Review 阶段直接修改；将其关联到现有任务或新任务，再由本 Skill 实施修复。修复完成后重新进入 Review，直至不存在阻断项。

所有实施过程中生成或更新的项目文档、注释、示例和文件链接只使用仓库相对路径，不得写入本机绝对路径、盘符、用户目录或 IDE 专用地址。

需要建立提交、同步分支或推送远端时使用 `$git-workflow`。代码实现完成不自动授权提交或推送。
