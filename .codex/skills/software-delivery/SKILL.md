# 软件交付

将请求转化为边界清晰、可验证的变更。从需求分析开始；不要为尚未采用的技术、仓库结构或项目管理体系强加规则。对于只有一句话或一个想法的输入，先澄清再规划，不要用模型推测补齐产品需求。

## 需求分析流程

1. 先读取适用的仓库指令。定位最近的 `AGENTS.md`，以及其中引用的任务、Issue、Roadmap、决策或架构记录。以项目本地指令为该项目的事实来源。
2. 在提出实现方案前，检查相关代码、测试、配置和文档。将有证据的事实与推断明确区分。
3. 先写出对请求的临时理解，不把理解当成需求。明确列出已经知道的内容、尚未知道的内容，以及哪些未知会阻塞后续工作。
4. 对阻塞性未知项提出澄清问题。按主题分批沟通，每轮通常只提出 1-3 个当前最关键的问题；优先使用有上下文的选择题，并为每题保留用户回答位置。等待用户确认，不得在未确认前擅自实现或创建完整方案。
5. 将用户回答合并回需求简报。简报包含目标、受影响的用户或调用方、范围内行为、明确的非目标、验收条件、受影响边界、约束、假设、风险和验证方式。
6. 对仍存在的未知项分类：
   - 答案可从仓库中直接、明确获得时，基于证据解决。
   - 仅当不改变产品行为、公开契约、安全、成本或架构时，才可做可回退、低影响的技术假设；必须声明假设和回退方式。
   - 会改变行为、API 契约、数据处理、安全、成本、架构或交付范围时，实施前必须请求决策。
7. 让问题具备决策条件。提供理解取舍所需的上下文和证据；必要时给出少量有实质差异的选项，并标明推荐选项。按照仓库规则记录应长期保留的决策。
8. 只有在需求简报得到确认后，才进入计划拆分。将已确认的简报拆分为小任务；每个任务必须有可观察的结果、验证方式和受控的改动范围，不得混入无关清理。

## 范围规则

- 除非任务明确要求变更，否则保持现有架构和约定。
- 不要从实现细节、注释或单个测试中臆造产品需求；此类结论必须标记为推断。
- 将缺陷现象与根因分开。选择修复方案前，先复现问题或建立其他有效证据。
- 验收条件必须可观察：描述输入、输出、状态变化、错误行为及相关非功能性约束。
- 存在兼容性、迁移、回退、数据丢失、隐私或运维风险时，必须明确说明。
- 产物应与工作规模相称。边界清楚的小改动可以只在任务记录中保留简短简报；功能、契约变更或长期决策需要维护正式文档。

## 澄清与文档沟通

- 将用户的原始表达、Agent 的理解、已确认事实和待确认问题分开书写。
- 不要虚构用户、角色、业务规则、接口字段、指标、异常行为或验收标准。缺少证据时标记为未知。
- 默认先完成澄清，不默认边澄清边实现。只有用户明确授权“先按假设做原型”时，才可在标注假设的前提下推进。
- 问题文档应聚焦一个主题，记录背景、已知证据、待确认问题、选项、推荐方案和回答区。用户回答后更新原文档，不另起一份互相竞争的记录。
- 默认将可枚举的决策写成选择题，每题提供 2-4 个有实际差异的选项，并提供 `其他，请说明：` 或 `暂不确定，请先给出建议：`。只有产品愿景、特殊约束、补充背景等无法合理枚举的内容才使用开放题。
- 选项必须基于仓库证据或明确标注为 Agent 建议；不得把推荐方案写成已确认事实，也不得为了“完整”一次列出所有可能问题。
- 每轮问题只覆盖一个主题。用户回答后更新原问题文档并重新检查剩余阻塞项，再决定是否提出下一轮问题。
- 生成问题文档后检查编号、标题和 Markdown 结构，删除残留的模板占位符或异常文本（例如 `问题UN.`）。
- 需求确认后，将问题文档与需求简报互相链接；长期有效的结论再转入决策或规范文档。
- 文档目录和所有权遵循仓库 `AGENTS.md`；仓库没有约定时，先使用 `$codex-project-bootstrap` 建立项目规则和文档结构。
- 所有写入项目的文档和其中的文件链接只使用仓库相对路径；不得写入本机绝对路径、盘符、用户目录或 IDE 专用地址。

## 实施前交接

实施前，提供或更新包含以下内容的需求简报：

- 目标与非目标
- 证据与假设
- 验收条件
- 受影响的组件与接口
- 待决策事项、决策人和建议的下一步
- 拟采用的验证方式

定义范围、记录决策或编写需求简报时，读取 [references/requirements-analysis.md](references/requirements-analysis.md)。需求确认后，用户界面使用 `$frontend-design`，系统结构或接口使用 `$software-architecture`；无需独立设计时再使用 `$delivery-planning`。需求范围仍不清晰时，继续停留在本 Skill 的澄清阶段。
