# 需求分析参考

## 证据分级

存在歧义时，在简报中使用以下标签：

- **已确认：** 请求方直接说明，或由代码、测试、配置、已批准的项目记录明确证明。
- **推断：** 基于部分证据的合理结论；未经确认不得视为需求。
- **假设：** 为推进可回退工作而暂时作出的选择；说明影响和复查时点。
- **待决策：** 备选方案会改变行为、成本、安全、范围或架构，因此需要负责人决断的选择。

## 需求简报模板

```md
# [变更标题]

## 目标

[需要实现的用户或业务结果。]

## 范围

- 范围内：[行为或系统边界]
- 非目标：[明确排除的工作]

## 证据与假设

- 已确认：[证据及来源]
- 推断：[推断内容及尚未确认的原因]
- 假设：[可回退假设及影响]

## 验收条件

1. 给定[前置条件]，当[执行动作]时，应当[可观察结果]。
2. [存在时补充错误、兼容性、性能、安全或无障碍条件。]

## 影响

- 组件与接口：[受影响区域]
- 数据与迁移：[无或详细说明]
- 风险与回退：[无或详细说明]

## 验证

- 自动化：[针对性测试、类型检查、Lint、构建]
- 人工或运维：[场景、环境、观察点]

## 待决策事项

1. [决策问题]
   - 方案 1：[取舍]
   - 方案 2：[取舍]
   - 建议：[方案及原因]
   - 决策人 / 答复：[确认前留空]
```

## 澄清问题模板

```md
# [问题主题]

## 背景

[说明当前请求和为什么需要确认。]

## 已知证据

- [来自用户、代码、测试或项目文档的事实]

## 问题 1

[一次只问一个可决策的问题。每轮只围绕一个主题，通常包含 1-3 个问题。]

1. [方案 A 及其影响]
2. [方案 B 及其影响]
3. [方案 C 及其影响]
4. 其他，请说明：
5. 暂不确定，请先给出建议：

推荐：[选项及理由]

回答区：

## 确认后的处理

[用户回答后填写：结论、影响范围、需要更新的需求或决策文档。]
```

问题文档不应替 Agent 隐藏不确定性，也不应把推荐方案伪装成用户已经做出的决定。

## 问题设计规则

- 默认使用选择题。选项数量通常为 2-4 个，必须有真实的行为、范围、成本、风险或维护差异。
- `其他，请说明：` 和 `暂不确定，请先给出建议：` 是兜底入口，不代表 Agent 可以跳过澄清或替用户做决定。
- 只有无法合理枚举的内容才使用开放题，例如一句话产品愿景、特殊合规约束、已有外部承诺或补充背景。开放题也必须保留回答区。
- 选项若不是证据支持的事实，必须标注为“建议”或“待确认方案”；推荐项只表达建议，不改变状态。
- 一次问题文档只聚焦一个主题；回答完成后更新原文档，记录结论和影响，再创建下一轮问题（如仍有阻塞项）。
- 在写入项目之前检查文档的编号、标题、列表和回答区，确保没有残留占位符、乱码或类似 `问题UN.` 的异常文本。

## 决策阈值

当选择会改变以下任一项时，必须在实施前询问：

- 用户可见行为或用户体验
- 公开 API 或跨服务 API 契约
- 持久化数据、迁移、保留策略或隐私
- 身份验证、授权、安全或合规
- 持续性运维成本或供应商依赖
- 架构、模块归属或兼容性承诺

只有决策易于回退且不触及上述阈值时，才可在声明假设后继续推进。

## 质量检查

实施前，确认简报回答了以下问题：

1. 谁将发生什么变化？
2. 哪些内容必须保持不变？
3. 哪些证据支持当前范围？
4. 如何判断成功，以及如何发现回归？
5. 哪些未知项仍需要负责人决策？
