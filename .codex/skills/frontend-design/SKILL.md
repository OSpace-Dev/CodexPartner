# 前端界面设计

在需求确认后定义用户如何完成任务，以及界面需要呈现什么。输出可审查的设计规格，不直接修改产品代码，也不把文本模型的猜测当成用户需求或最终视觉稿。

## 设计准入

开始前确认：

- 用户或使用角色、核心任务、范围和验收条件已经确认。
- 目标平台、设备、输入方式和关键内容或数据已知。
- 已读取适用的 `AGENTS.md`、现有产品界面、设计系统、品牌规范和前端技术约束。

缺少产品行为、页面目标或关键内容时，使用 `$software-delivery` 继续澄清。

## 设计流程

1. 建立现状与约束。检查已有导航、页面、组件、内容、设计令牌和用户流程；已有产品优先保持一致性。
2. 定义用户流程。说明入口、前置状态、用户动作、系统反馈、成功结果、失败恢复和离开路径。
3. 组织信息架构。确定导航、页面层级、内容优先级和跨页面关系，避免按后端数据表机械设计界面。
4. 为每个页面或视图定义目的、进入与退出条件、布局区域、内容层级、主要动作、次要动作和数据依赖。
5. 定义完整状态：默认、加载、空、错误、成功、禁用、权限不足、离线、部分数据和长内容等适用状态。
6. 定义组件和交互。优先复用现有设计系统；说明控件类型、行为、校验、反馈、焦点、键盘、触摸和撤销等适用规则。
7. 定义响应式和可访问性。说明关键断点或容器规则、内容重排、最小点击区域、对比度、语义、焦点顺序和辅助技术要求。
8. 定义视觉方向和资源需求。描述颜色、排版、密度、图标、图片、图表或动效的用途与约束，不用空泛形容词替代可验证要求。
9. 建立页面级验收标准，并将需要 API、权限、数据或系统行为支持的内容反馈给 `$software-architecture`。
10. 输出面向下游工具的交接规格，明确目标画布、视口、页面、状态、组件、资源、约束和期望产物。

## 设计边界

- 不虚构用户角色、业务流程、页面内容、数据字段、品牌资产或产品功能；未知内容必须澄清或标注。
- 不为操作型产品套用营销落地页结构，也不为内容型产品强行使用高密度后台布局；设计应匹配任务和使用频率。
- 不只设计理想状态；错误、空数据、权限、等待和恢复路径同样属于设计范围。
- 不用视觉稿掩盖未确认的产品或 API 决策。
- 不输出机器绝对路径。文档、资源引用和下游工具输入只使用仓库相对路径或公开 URL。

## 设计交付

设计文档使用 `YYYY-MM-DD-NNN-topic.md`，正文编号为 `UI-YYYYMMDD-NNN`。根据任务规模交付：

- 用户流程与信息架构
- 页面或视图清单
- 页面级界面与交互规格
- 组件和状态矩阵
- 响应式与可访问性规则
- 视觉资源需求
- 面向 Figma、图像生成、原型或前端实现工具的交接说明
