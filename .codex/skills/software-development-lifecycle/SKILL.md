# 软件全生命周期导航

读取项目事实，判断当前阶段，再调用最少数量的专项 Skill。不要一次性加载所有 Skill，也不要把总控导航当成具体执行流程。

## 路由流程

1. 读取适用的 `AGENTS.md` 和其中引用的文档导航、任务、需求、设计、评审、测试、部署或运维记录。
2. 明确用户当前目标、已完成产物、最近一次有效状态和阻塞项。不能从证据确认时，标记为未知，不猜测阶段已完成。
3. 根据 [references/lifecycle-map.md](references/lifecycle-map.md) 选择当前阶段和专项 Skill。
4. 检查当前阶段的准入条件。上游产物缺失或失效时，回到最近的必要阶段，不用下游工作弥补上游决策。
5. 调用适用的专项 Skill。只在界面与架构、修复与复审等确有交叉时组合少量 Skill，并说明执行顺序。
6. 专项阶段完成后记录产物、结论、未决问题和下一阶段。用户要求继续端到端推进时，重新检查下一阶段准入条件后继续。

## 默认入口

- 新项目、空仓库、缺少 `AGENTS.md` 或需要整理项目协作规则：`$codex-project-bootstrap`
- 只有一句想法、目标模糊或产品行为未确认：`$software-delivery`
- 用户界面、页面流程或交互需要设计：`$frontend-design`
- 系统边界、组件、数据、API、协议、部署拓扑或复杂实现需要设计：`$software-architecture`
- 需求和适用设计已确认，需要拆分里程碑或任务：`$delivery-planning`
- 任务已 Ready，需要修改代码、测试、配置或技术文档：`$software-implementation`
- 实现及开发者级验证完成，需要独立检查：`$software-review`
- 评审通过，需要自动化与人工测试或验收：`$software-testing`
- 测试通过，需要发布到目标环境：`$software-deployment`
- 明确版本已部署，需要观察、维护或恢复：`$software-operations`

## 横向能力

- 初始化仓库、配置远端、管理分支、提交、推送、合并、标签或历史：`$git-workflow`
- 编码、重构、Review 或建立项目编码规范：`$code-quality`
- 横向 Skill 与当前阶段组合使用，不替代阶段准入和质量门槛。
- 调用 `$git-workflow` 不代表用户已经授权提交、推送、合并或历史改写；每项外部或高风险操作仍按仓库规则确认。

## 阶段控制

- 小型低风险任务可以不建立独立设计或里程碑文档，但不能跳过需求边界、实现验证、评审和必要测试。
- 前端设计与架构设计可以并行迭代；涉及数据、权限或接口时必须在规划前对齐。
- Review 只报告问题，不修改代码；发现回流到 `$software-implementation`，修复后重新 Review。
- 测试发现缺陷时回流实现和评审；不得在测试阶段直接修复产品代码。
- 部署失败或运维发现缺陷时先恢复稳定状态，再根据问题性质回流需求、设计或实现阶段。
- 任何阶段出现影响行为、契约、数据、安全、成本或架构的新未知项时，暂停并请求决策。

## 输出

每次路由只需说明：

- 当前阶段及证据
- 选择的 Skill 及原因
- 已满足和未满足的准入条件
- 本阶段预期产物
- 完成后进入哪个阶段

所有生成文档、路径和链接遵循项目 `AGENTS.md`，并只使用仓库相对路径。
