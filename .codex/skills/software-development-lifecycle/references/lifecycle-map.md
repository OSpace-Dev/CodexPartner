# 软件生命周期地图

## 主流程

```text
项目初始化（缺少项目规则时）
  -> 想法或问题
  -> 需求澄清
  -> 界面设计（适用时）
  -> 架构与 API 设计（适用时）
  -> 交付规划
  -> 编码实现与开发者级验证
  -> 只读评审
  -> 自动化与人工测试
  -> 部署
  -> 运行维护
```

## 路由表

| 现有证据 | 当前缺口 | 路由 |
| --- | --- | --- |
| 新项目或缺少项目指令 | `AGENTS.md`、文档所有权和协作规则 | `$codex-project-bootstrap` |
| 只有想法或问题 | 目标、范围、验收 | `$software-delivery` |
| 需求已确认且有用户界面 | 流程、页面、状态、交互 | `$frontend-design` |
| 需求已确认且改变系统边界 | 架构、数据、API 或详细设计 | `$software-architecture` |
| 需求和适用设计已确认 | 依赖、里程碑、任务 | `$delivery-planning` |
| Ready 任务 | 实现和开发者级验证 | `$software-implementation` |
| 实现已完成 | 独立风险检查 | `$software-review` |
| Review 已通过 | 正式测试和人工验收 | `$software-testing` |
| 测试已通过 | 发布、验证和回退 | `$software-deployment` |
| 已部署明确版本 | 观察、维护和恢复 | `$software-operations` |

## 回流规则

- 设计发现产品行为不清晰：回到 `$software-delivery`。
- 规划发现架构或接口不可拆解：回到 `$software-architecture`。
- Review 发现实现问题：回到 `$software-implementation` 后复审。
- 测试发现缺陷：回到实现和 Review，再重跑受影响测试。
- 部署失败：先回退；代码或配置问题进入相应实施流程。
- 运维发现长期问题：临时缓解与正式修复分开，正式修复进入适用的上游阶段。

## 横向能力

- `$code-quality` 在实现和 Review 中提供编码原则与坏味道判断，不单独改变任务状态。
- `$git-workflow` 在仓库初始化、同步、提交、评审协作、发布和恢复时使用，不把托管平台绑定到主流程。

## 产物门槛

阶段是否完成以证据为准，而不是以对话中声称“完成”为准。证据可以是已确认文档、代码差异、评审报告、测试结果、部署记录或运行状态；所有项目文件引用使用相对路径。
