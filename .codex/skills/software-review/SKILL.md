# 软件评审

独立评审已经完成的变更，只报告问题、证据和风险，不修改代码。评审问题必须回流到 `$software-implementation` 处理，再由本 Skill 复审。评审通过后使用 `$software-testing` 进入正式测试与验收。

## 评审准入

开始评审前获取：

- 已确认的需求、任务范围、非目标和完成定义。
- 待评审的完整变更集，包括代码、测试、配置和文档。
- 实施者已执行的开发者级验证及其结果。
- 适用的 `AGENTS.md`、决策记录、接口或技术规范。

信息缺失时仍可评审已有内容，但必须降低结论置信度并列出缺口。不要用猜测补齐预期行为。

## 只读边界

- 不修改源代码、测试、配置、文档、任务状态或评审范围内的任何文件。
- 不运行自动修复、格式化、代码生成、依赖安装、迁移或其他可能改写工作区的命令。
- 可以读取文件、差异、历史和规范，也可以运行不会改写受控文件的诊断或测试命令。
- 命令可能产生缓存或临时文件时，先确认其位置和仓库规则；无法确认时不运行，并在报告中说明。
- 即使评审者已经知道修复方式，也只描述期望行为、影响和修复方向，不直接提交补丁。

## 评审流程

1. 读取适用指令、需求、任务和决策，建立“变更应该做什么、不能改变什么”的评审基线。
2. 检查完整差异和受影响调用链，不只阅读改动行。识别新增、删除、生成和意外修改的文件。
3. 追踪关键行为的正常路径、错误路径和边界条件。按实际技术域检查契约、状态、数据、权限、并发、资源、性能和兼容性；使用 `$code-quality` 判断影响维护与正确性的真实坏味道，不报告纯个人风格偏好。
4. 检查测试是否真正覆盖变更行为和回归风险，是否存在只验证实现细节、错误断言或被跳过的测试。
5. 对每个候选问题建立可复核证据。说明触发条件、代码位置、实际行为、预期行为和影响；不能证明的问题标记为疑问或风险，不伪装成缺陷。
6. 合并重复问题，按严重程度排序。优先报告会导致错误行为、数据或安全风险、兼容性破坏和关键测试缺口的问题，不将个人风格偏好升级为缺陷。
7. 输出评审报告和结论。不得在同一评审步骤中修复问题。

## 严重程度

- `P0`：会造成灾难性安全、数据、生产或不可恢复影响，必须立即阻断。
- `P1`：在正常或高概率场景中造成严重错误，必须在进入测试前修复。
- `P2`：在特定场景中造成实际缺陷、回归或明显维护风险，应在当前交付中修复。
- `P3`：低影响但有证据的问题，可由项目决定当前修复或进入 Backlog。

不要报告没有行为影响的纯格式或个人偏好问题，除非它明确违反仓库规则。

## 报告要求

- 先列发现，按 `P0` 到 `P3` 排序；每项包含唯一编号、位置、触发场景、证据、影响和修复方向。
- 文件位置尽量精确到最小相关行；跨文件问题列出主位置并说明关联范围。
- 发现之后列出开放问题、未检查内容和残余风险。
- 明确给出结论：`阻断`、`有条件通过` 或 `通过`。
- 没有发现问题时明确写“未发现阻断性问题”，同时说明测试缺口或无法覆盖的风险。

## 问题回流与复审

1. 将评审报告保存为 `YYYY-MM-DD-NNN-topic.md`，正文编号使用 `REV-YYYYMMDD-NNN`。
2. 将每项发现编号为 `REV-YYYYMMDD-NNN-F001`、`F002` 等；编号一经分配不得重排。
3. 由 `$delivery-planning` 将需要处理的发现转化为任务，或关联到现有任务。
4. 由 `$software-implementation` 完成修复和开发者级验证；Review 阶段本身不修改代码。
5. 复审时逐项记录 `已解决`、`仍存在`、`不修复并已接受风险` 或 `无法验证`，保留原始发现历史。
6. 不存在未解决的 `P0`、`P1` 和项目规定的阻断项后，才进入正式测试与验收阶段。

评审时读取 [references/review-guide.md](references/review-guide.md) 使用检查项和报告模板。

评审报告中的文件链接和路径只使用仓库相对路径；位置引用采用相对路径加行号，不得写入本机绝对路径、盘符、用户目录或 IDE 专用地址。
