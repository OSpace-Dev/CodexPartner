# 项目初始化问题顺序

项目为空或缺少可用上下文时，不要把所有未知信息一次性变成问卷。根据当前阶段分批确认；每批回答后重新检查仓库和阻塞项。

## 第一轮：目标与交付形态

只确认会决定项目边界的内容，通常 1-3 题：

1. 项目当前更接近哪一种：面向用户的界面应用（含 Web、浏览器扩展、桌面或移动端）、后端服务或数据处理、命令行/设备端程序，还是库/SDK/开发者工具？
2. 首个可交付结果更接近哪一种：可运行原型、最小可用版本、内部工具、生产版本、技术验证，或其他？
3. 主要使用者更接近哪一种：个人使用、固定团队或企业内部用户、公开用户，还是其他开发者/系统集成方？

如果项目类型或首个交付结果尚未明确，先停在这一轮，不生成技术栈、命令或部署问题。

## 第二轮：技术路线与运行环境

只有第一轮已确认，且技术选择会阻塞后续初始化时才询问：

1. 技术路线：沿用仓库已有技术、选择 Agent 推荐的主流方案、由负责人指定方案，或暂不确定请先给建议。
2. 运行环境：本地单机、容器、云服务器、企业内网、浏览器/移动设备、嵌入式设备，或其他。
3. 交付渠道：本地运行、压缩包/制品交付、容器部署、应用商店/插件商店、内部发布，或其他。

不要假定具体语言、框架、版本、Manifest、云厂商或服务器规格；这些应作为本轮选项的待确认内容，或依据仓库证据填写。

## 第三轮：协作与验证约束

产品和技术路线确认后，再确认会影响执行的约束：

1. Git 状态：尚未初始化、已有本地仓库、已有远端仓库，或需要先确认远端与分支策略。
2. 验证条件：自动化测试为主、人工验收为主、两者结合，或当前只能做基础检查。
3. 特殊边界：无特殊限制、涉及隐私/安全/合规、存在禁止修改目录、需要审批的外部操作，或其他。

## 生成规则

- 每一轮生成一份有编号的问题文档，但同一轮的紧密相关问题放在同一文档中。
- 文件名使用 `YYYY-MM-DD-NNN-topic.md`，文档内使用 `Q-YYYYMMDD-NNN`；创建前检查目标目录，递增当天同类编号。
- 每个问题使用阿拉伯数字选项，并在选项末尾保留 `其他，请说明：` 与 `暂不确定，请先给出建议：`（不适用时可删去其中一个）。
- 选项旁写清主要取舍；可给出“推荐”，但必须保持状态为“待确认”。
- 用户回答后在同一文档的“确认结果”或“回答区”填写结论、依据和影响，不创建重复问题文档。

## 问题文档最小格式

生成的问题文档至少使用以下结构，不要把问题写成无选项的开放问卷：

```md
# 项目目标与交付形态待确认

- 编号：`Q-YYYYMMDD-NNN`
- 状态：待确认
- 创建日期：YYYY-MM-DD
- 回答位置：本文“确认结果”一节

## 已知证据

- [仓库或用户已经明确的事实]

## 待确认问题

### 问题 1：项目类型

请选择最符合当前目标的一项：

1. Web 应用：主要通过浏览器访问。
2. 后端服务：提供接口、任务或数据处理能力。
3. 命令行、桌面、移动或嵌入式程序：需要本地或设备运行。
4. 库、SDK 或其他开发者工具：主要被其他程序集成。
5. 其他，请说明：
6. 暂不确定，请先给出建议：

推荐：暂不确定时由 Agent 根据证据给出建议，但不替用户确认。

回答区：

## 确认结果

等待用户回答。回答后记录结论、依据、影响范围和下一轮仍需确认的问题。
```

示例中的项目类型只是通用选项，不得当作当前仓库事实。实际生成时应根据证据调整选项，并删除不适用的选项。
