# 软件测试

验证变更是否满足已确认需求和完成定义。优先利用可重复的自动化检查；无法自动化时，交付清晰、可操作、可回填的人工测试协议，不把“请用户测试”当成完整测试方案。

## 测试流程

1. 读取需求、验收条件、任务、评审报告和适用的 `AGENTS.md`。将每条验收条件映射到一个或多个测试用例。
2. 识别测试范围、风险、环境、数据、权限、设备和外部依赖。明确哪些条件可由当前环境验证，哪些条件受限。
3. 为每个测试目标选择验证方式：现有自动化测试、值得新增的聚焦自动化测试、命令或检查工具、人工操作，或组合方式。需要新增测试代码时，先形成任务并回到 `$software-implementation` 实施和 `$software-review` 评审。
4. 先执行成本低且信息量高的自动化验证，再执行集成、环境、设备或人工验收。不要因为自动化缺失而跳过高风险场景。
5. 需要人工参与时，先生成测试协议并交付给用户。协议必须包含准备条件、逐步操作、预期结果、验收标准、证据要求和结果回填区；等待用户回填，不代替用户声称通过。
6. 记录每个用例的状态：通过、失败、阻塞、未执行或不适用。失败和阻塞项必须包含复现信息、证据和影响。
7. 发现实现缺陷时停止把该变更标记为通过，将问题关联到任务并回到 `$software-implementation` 修复；修复后重新经过 `$software-review` 和受影响测试。
8. 测试完成后输出测试报告，说明覆盖范围、执行方式、环境、证据、未覆盖项、剩余风险和最终建议。

## 自动化与人工的选择

- 自动化适合稳定、重复、可隔离、结果可客观判断的检查，例如单元、接口、类型、构建、静态分析和可重复回归。
- 人工适合真实设备、视觉和交互判断、外部服务、复杂部署、一次性环境或需要业务人员确认的场景。
- 不能自动化不等于不需要验证；将限制转化为人工步骤、明确观察点和可保存证据。
- 不能证明的内容必须标记为“未覆盖”或“阻塞”，不得用临近测试结果推断通过。
- 测试命令可能修改数据库、设备、外部服务或工作区时，先确认环境和回退方式；没有明确授权时不要执行破坏性测试。

## 测试阶段边界

- 本阶段可以创建测试方案、人工协议、执行记录和测试报告，但不直接修改产品代码。
- 需要新增或修正自动化测试代码、夹具、模拟器或测试环境脚本时，将工作回流为实施任务，完成编码和评审后再恢复正式测试。
- 发现缺陷时记录复现步骤和证据，不在测试阶段顺手修复。
- 人工执行结果只能由实际执行者回填；Agent 不得代填“通过”。

## 人工验收交付

交付给用户的测试协议必须让未参与编码的人也能独立执行，至少包含：

- 测试目的和对应需求编号
- 测试环境、版本、账号、设备、数据和前置状态
- 按顺序编号的操作步骤
- 每一步的预期结果和关键观察点
- 通过、失败、阻塞和不适用的判定标准
- 截图、日志、录屏、输出或其他证据要求
- 结果填写区、执行人、执行时间和环境信息

用户回填结果后，保留原始协议和结果，不只在对话中记录“已测试”。

## 通过门槛

只有在以下条件满足或由负责人明确接受风险后，才能建议通过：

- 所有关键验收条件都有通过证据。
- 评审遗留的阻断项已解决并复审通过。
- 自动化检查已执行且结果可解释。
- 必需的人工、环境或设备用例已完成，或明确记录为阻塞并由负责人接受。
- 失败项、未覆盖项和剩余风险已记录。

使用 [references/testing-guide.md](references/testing-guide.md) 创建测试用例、人工协议和测试报告。测试文档按 `YYYY-MM-DD-NNN-topic.md` 命名，并在正文设置 `TEST-YYYYMMDD-NNN` 编号。测试通过后使用 `$software-deployment` 进行发布准入和部署。

测试方案、证据位置和测试报告中的仓库文件链接只使用相对路径；本机环境差异使用变量或通用占位符描述，不得记录绝对路径、盘符、用户目录或 IDE 专用地址。
