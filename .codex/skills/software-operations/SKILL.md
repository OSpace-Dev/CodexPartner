# 软件运行维护

维护已经部署的明确版本，使系统可观察、可恢复并保持在已知状态。首次部署使用 `$software-deployment`；需要代码修复或功能变化时回到需求、规划、实现、评审和测试流程。

## 运维准入

开始前确认：

- 目标环境、服务、版本、实例或设备可以唯一识别。
- 已读取适用的 `AGENTS.md`、部署记录、运行手册、监控、备份和回退说明。
- 当前操作目的、影响范围、权限、成功标准和恢复方式明确。

无法确认目标或版本时只做只读调查，不执行重启、清理、写入或配置变更。

## 运维流程

1. 识别目标和基线。记录环境、版本、健康状态、依赖和当前告警，不依赖模糊的“线上”或“服务器”称呼。
2. 优先进行只读观察：健康检查、日志、指标、资源、队列、证书、备份状态和配置差异。
3. 判断工作类型：例行检查、维护操作、容量调整、备份恢复、故障缓解或升级需求。
4. 对会修改外部状态的操作说明目标、命令或动作、预计影响、停止条件和恢复方式，并取得必要确认。
5. 小步执行，每一步后核对实际状态。不要把多个高风险动作隐藏在无法中断的命令中。
6. 完成后验证服务健康、关键功能、日志、指标和数据状态，并记录实际结果。
7. 发现代码、架构或需求问题时保存证据并创建回流项，不在运维阶段直接修改产品代码。

## 常见工作

- 健康与可观察性：可用性、错误率、延迟、吞吐、资源和关键业务信号。
- 例行维护：证书、磁盘、日志保留、备份校验、计划任务和依赖服务状态。
- 配置与漂移：对比批准配置和实际状态，敏感值只验证存在性与来源，不写入文档。
- 容量与性能：趋势、瓶颈、阈值和扩缩容建议，避免仅凭单次采样下结论。
- 备份与恢复：备份成功不等于可恢复；按风险定期验证恢复流程和数据完整性。
- 故障响应：先控制影响并保留证据，再定位根因；临时缓解与永久修复分开记录。

## 安全边界

- 删除、重启、切流、恢复、生产写入、权限和配置变更必须明确目标并具备恢复方案。
- 不记录密钥、令牌、完整连接串、真实个人身份或本机和服务器绝对路径。
- 不用通配符、未解析变量或宽泛目录执行破坏性操作。
- 不为消除告警而关闭监控、降低安全控制或删除证据。
- 紧急缓解后仍需建立正式修复任务，并重新经过适用的交付流程。

## 运维交付

运维文档使用 `YYYY-MM-DD-NNN-topic.md`，正文编号为 `OPS-YYYYMMDD-NNN`。操作记录至少包含目标版本、环境、前置状态、动作、证据、结果、影响、恢复状态和后续事项。

需要人工操作时，输出逐步运行手册，包含每一步预期结果、停止条件、失败处理和回填区。使用 [references/operations-guide.md](references/operations-guide.md) 创建运行手册和维护记录。
