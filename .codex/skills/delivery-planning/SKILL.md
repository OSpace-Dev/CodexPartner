# 交付规划

把已确认的需求转化为足以指导交付的计划。规划服务于实施和验证，不替代需求分析，也不强制每项工作都建立 Roadmap 或 Milestone。

## 规划流程

1. 以已确认的需求简报和适用的界面、架构、API 或详细设计为输入。检查目标、非目标、验收条件、设计约束、假设、待决策项和验证方式；高影响未知项未决时，回到需求分析或相应设计阶段，而不是直接拆任务。
2. 识别影响面与约束：受影响模块、接口和数据，现有测试与构建边界，依赖团队或外部系统，以及时间、发布或兼容性限制。
3. 按工作规模选择最小的计划层次：
   - 小型、单一边界、低风险改动：只创建一个可执行任务。
   - 需要多步验证或有明确依赖的变更：创建一个里程碑和多个任务。
   - 多个独立成果、长期方向或跨项目协调：创建 Roadmap、里程碑和任务。
4. 先定义按结果划分的里程碑。每个里程碑应描述可观察的交付状态、验收标准、前置依赖和风险，而不是仅列技术活动。
5. 将里程碑拆分为内聚任务。每个任务只解决一个可验证问题，说明范围、非目标、依赖、完成定义、验证方式和需要更新的文档。
6. 排列任务顺序。优先处理能尽早验证关键假设、解除后续依赖或降低最大风险的工作；标记可并行和必须串行的任务。
7. 发布计划时明确当前可开始的任务、阻塞项、负责人或决策人，以及计划假设。实施过程中，范围或证据变化时更新计划并说明原因。

## 任务边界

- 任务应小到能在一个连续工作周期内完成、验证并收口；过大时按可交付结果继续拆分。
- 任务标题描述结果或问题，不使用“处理”“优化”等无法验收的词。
- 不要按文件、层次或个人角色机械切分；按可独立验证的行为、风险或边界切分。
- 同一任务不混入无关重构、格式化或机会性清理。必要清理单独进入 Backlog。
- 开始任务前，确认其前置条件已满足，或将其明确标记为阻塞。
- 任务完成不等于代码已写完。完成条件至少覆盖目标、验证、必要文档和已知风险的记录。

## 计划维护

- 计划是当前交付意图的记录，不是对未来的虚假承诺。新证据出现时及时调整。
- 保留需求、决策、任务和验证记录之间的可追溯关系，但不要在多个位置重复维护同一事实。
- 发现新的不阻塞问题时放入 Backlog；不要静默扩大当前任务范围。
- 里程碑完成后，记录验收结果、未解决风险和可复用经验。

## 实施前交接

实施前，确保当前任务具备：

- 可观察的目标和验收条件
- 明确范围与非目标
- 已满足或已标注的依赖
- 最小受影响范围
- 具体的验证方式
- 必要的决策、文档或回退要求

需要创建或复核计划时，读取 [references/planning-templates.md](references/planning-templates.md)。需求范围仍不清晰时，使用 `$software-delivery` 回到需求分析。

所有规划文档和其中的仓库文件链接只使用相对路径，不得写入本机绝对路径、盘符、用户目录或 IDE 专用地址。
