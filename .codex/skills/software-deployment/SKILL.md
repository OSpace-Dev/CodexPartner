# 软件部署

将已通过测试的软件版本安全地交付到目标环境。用一次命令编排可检查、可观察、可回退的步骤，但不以“一键”为由隐藏目标、跳过确认或取消安全门槛。

## 发布准入

部署前确认：

- 目标版本、提交或制品唯一且可追溯。
- `$software-testing` 的结论满足发布要求，阻断项已经关闭或由负责人明确接受风险。
- 目标环境、配置来源、权限、数据影响、停机影响和依赖明确。
- 健康检查、验收方式、失败判定和回退方案可以执行。
- 数据迁移、备份和破坏性操作已经单独确认。

缺少部署脚本、Dockerfile、流水线或环境配置时，不要在部署时临时拼接。先用 `$delivery-planning` 建立任务，经 `$software-implementation`、`$software-review` 和 `$software-testing` 完成后再部署。

## 策略选择

根据交付对象选择最小可行策略：

- 静态站点：构建静态制品，上传对象存储、CDN 或静态托管平台并验证缓存与回退。
- 后端或全栈服务：使用平台发布、预构建镜像，或源码包上传后在服务器构建容器。
- 桌面与移动应用：生成签名安装包，通过测试渠道、商店或受控下载分发。
- 系统与嵌入式：生成固件或系统制品，记录硬件版本、刷写方法、兼容性和恢复流程。
- 数据与配置：将迁移视为独立高风险步骤，先备份、验证兼容性并准备回滚或前滚方案。

个人或小型后端项目优先考虑 [references/remote-docker-build.md](references/remote-docker-build.md) 中的“本地源码包 + 远端 Docker 构建”策略。

## 部署流程

1. 读取适用的 `AGENTS.md`、测试报告、部署配置和环境说明。确认部署目标、版本和批准人。
2. 执行预检：工具、连接、磁盘、端口、Docker、运行时、配置和依赖服务。预检失败时停止，不进入半部署状态。
3. 生成不可变发布标识和制品。创建清单及 SHA-256 校验值，排除密钥、本地配置、缓存和无关文件。
4. 在执行外部变更前展示目标环境、版本、主要动作、数据影响、预计停机和回退方式，并取得明确确认。
5. 传输并校验制品。服务器端校验通过后才解压到新的发布目录，不覆盖当前可用版本。
6. 按选定策略构建和启动。敏感配置从目标环境注入，不写入源码包或镜像层。
7. 执行健康检查和必要的部署后验收。未满足通过标准时停止流量切换或立即回退。
8. 记录实际部署版本、环境、时间、执行人、命令结果、健康证据和回退状态。
9. 成功后按明确保留策略清理旧制品；不得在新版本验证前删除最后一个可用版本。

## 一键部署约束

“一键部署”应是一个稳定入口，例如项目定义的 `deploy` 命令，其内部至少包含：

```text
preflight -> package -> checksum -> transfer -> verify -> build -> start -> health -> record
```

- 支持 `dry-run` 或等价预览，展示将操作的环境、版本和资源。
- 生产环境要求显式指定目标，避免依赖模糊默认值。
- 每一步失败立即停止，并保留足以诊断和回退的状态。
- 日志不得输出密钥、令牌或完整敏感配置。
- 删除、迁移、切流和生产写入等高风险动作需要独立确认，不能被“一键”隐式授权。
- 同一发布标识重复执行时应可检测已有状态，避免意外创建冲突实例或重复迁移。

## 失败与回退

- 健康检查失败、关键依赖不可用、迁移失败或人工验收失败时，不得宣布部署成功。
- 回退使用已验证的上一版本、配置和数据策略；不要现场猜测回退命令。
- 无法自动回退时，生成逐步人工恢复协议，并明确每一步的预期状态和停止条件。
- 回退完成后仍需执行健康检查并记录事件；后续修复重新进入实现、评审和测试流程。

使用 [references/deployment-guide.md](references/deployment-guide.md) 创建部署计划、执行记录和人工操作协议。部署文档按 `YYYY-MM-DD-NNN-topic.md` 命名，正文编号使用 `DEP-YYYYMMDD-NNN`。

部署文档中的仓库文件引用只使用相对路径。服务器目录使用项目配置名、环境变量或如 `<deploy-root>` 的通用占位符，不记录本地开发机或真实服务器的绝对路径和身份信息。

部署成功并形成明确版本记录后，使用 `$software-operations` 进行持续观察和运行维护。
