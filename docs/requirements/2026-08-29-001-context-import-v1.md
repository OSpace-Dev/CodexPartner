# 上下文引入 v1

需求编号：`REQ-20260829-001`
状态：已确认实施范围，协议结构化能力采用兼容性假设

## 目标

让用户可以把 VS Code 项目中的编辑器选区作为独立上下文项加入当前 Codex Composer，并以内嵌小气泡的形式插入输入框中的任意光标位置；发送时保留用户指令与上下文的相对位置，并兼容当前 App Server 的纯文本输入契约。

## 范围

- 范围内：保存文件编辑器选区的工作区相对路径、1-based 行号范围和短摘要。
- 范围内：从 Code Action 添加多个上下文项，在 Composer 输入框内按光标位置展示、删除和继续编辑。
- 范围内：上下文项可以单独存在，用户可以只发送上下文而不额外输入指令。
- 范围内：发送前由扩展宿主将上下文项序列化为可诊断的纯文本提示。
- 非目标：本里程碑不实现文件夹、终端、诊断、搜索结果、Git diff 等其他来源。
- 非目标：本里程碑不改造 App Server 协议，不读取登录凭据，不实现审批 UI 或 Markdown 渲染。

## 证据与假设

- 已确认：当前编辑器 Code Action 已能识别选区，并把工作区相对文件路径和行号插入 Composer。
- 已确认：当前 `turn/start` 使用 `input: [{ type: "text", text }]` 发送文本。
- 已确认：项目核心卖点是把项目任意部分文本引入为每次对话上下文。
- 假设：App Server 当前版本不要求扩展传入原生结构化文件引用；M1 先用纯文本兼容格式承载 `ContextItem`。
- 假设：上下文项只属于当前 Composer 草稿，发送成功后清空，不写入扩展持久化存储。

## 验收条件

1. 给定保存文件中的非空选区，当用户触发“添加到 Codex Partner 对话”时，Composer 在最近一次光标位置插入一个上下文气泡，包含工作区相对路径和 1-based 行号范围。
2. 将光标放在已有文字中间添加选区时，气泡出现在前后文字之间，原有指令文本不丢失。
3. 连续添加至少两个选区时，两个上下文气泡按插入位置同时保留；用户可以单独删除任意气泡并继续在其前后输入文字。
4. 只有上下文项、没有指令文本时，发送操作仍可提交。
5. 发送时 App Server 仍收到一个 `input` 文本项；文本中包含上下文路径/行号和用户指令，且上下文与指令有明确分隔。
6. 发送成功后 Composer 清空；发送失败时保留当前输入和上下文，显示可诊断错误。
7. 扩展发送的路径只使用工作区相对路径，不把本机绝对路径写入消息或 UI。
8. 自动化测试覆盖上下文规范化、序列化、非法上下文拒绝和编辑器选区转换。

## 影响

- 组件与接口：扩展宿主的上下文队列、编辑器命令、侧栏 Webview Composer、`turn/start` 文本构造。
- 数据与迁移：无持久化数据，无迁移；上下文项只存在当前 Webview 草稿生命周期。
- 兼容性：不改变 App Server 客户端协议；未来可替换序列化函数以接入原生结构化输入。
- 安全：Webview 传来的上下文项由扩展宿主重新校验；路径只接受工作区相对路径，摘要限制长度。
- 回退：上下文无法规范化时拒绝发送该项并显示错误；纯文本消息仍按 M0 行为发送。

## 验证

- 自动化：`npm run check`，覆盖 Node.js 语法、上下文模型、inline 序列化和现有协议测试。
- 人工：在 Extension Development Host 中先输入前后文字，把光标放在中间，再添加两个选区；确认气泡位于正确位置，可继续编辑、删除、只发送上下文，并在失败时保留草稿。
